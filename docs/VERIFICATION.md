# Проверка проекта

Дата актуализации: 2026-09-06

Этот файл хранит актуальные команды проверки, ожидаемый результат и то, что пока не проверено.

## Быстрая автоматическая проверка

```bash
go test ./...
go test -race ./...
go vet ./...
go build ./...
```

Ожидаемый результат: команды завершаются без ошибок.

## Проверка с PostgreSQL

Нужна отдельная тестовая или локальная база. Никогда не используйте production-базу для экспериментов.

Задайте переменные окружения без добавления секрета в Git:

```bash
export DATABASE_URL=postgresql://localhost/uptime_control
export HTTP_ADDR=127.0.0.1:8080
export PUBLIC_ORIGIN=http://127.0.0.1:8080
export BASE_PATH=
export SESSION_COOKIE_SECURE=false
go run .
```

В другом терминале:

```bash
curl -i http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/ready
```

Ожидается:

- `/health` возвращает `200` и `{"status":"ok"}`;
- `/ready` возвращает `200` и `{"status":"ready"}`;
- при недоступной БД `/ready` возвращает `503`;
- повторный запуск приложения не применяет одну миграцию дважды;
- `Ctrl+C` корректно завершает собранный сервер.

## Последняя выполненная проверка

Среда:

- macOS arm64;
- Go 1.27.1;
- PostgreSQL 18.6;
- pgx/v5 5.10.0.

Успешно проверено:

- `gofmt`;
- `go test ./...`;
- `go test -race ./...`;
- `go vet ./...`;
- `go build`;
- подключение к чистой временной базе;
- применение `000001_initial_schema.up.sql`;
- наличие таблиц `users`, `sessions`, `sites`, `uptime_checks`, `incidents`, `schema_migrations`;
- повторный запуск без повторного применения миграции;
- ответы `/health` и `/ready` со статусом `200`;
- маршруты с `BASE_PATH=/uptimec` доступны только под `/uptimec`, а cookie получает `Path=/uptimec`;
- завершение собранного бинарного файла по `SIGINT` с кодом `0`;
- регистрация пользователя со статусом `201`;
- нормализация email к нижнему регистру;
- получение пользователя через cookie со статусом `200`;
- отзыв сессии при logout и последующий `401`;
- повторный вход со статусом `200`;
- Argon2id-хеш вместо пароля и 32-байтовый хеш токена в PostgreSQL;
- единая ошибка неверных учётных данных;
- отклонение чужого Origin со статусом `403`;
- ограничение попыток входа со статусом `429`;
- создание сайта владельцем со статусом `201`;
- список и изменение сайта владельцем со статусом `200`;
- одинаковый `404` для чужого и несуществующего сайта;
- блокировка literal private URL со статусом `400`;
- конфликт одинакового активного URL со статусом `409`;
- удаление без подтверждения со статусом `400`;
- мягкое удаление с подтверждением со статусом `204`;
- повторное создание URL после мягкого удаления;
- применение `000002_unique_active_site_url.up.sql`.

После проверки временная база удалена, PostgreSQL остановлен. Реальные пользовательские данные не создавались и не удалялись.

## Пока не проверено

- запуск на удалённом Linux-сервере;
- работа за reverse proxy и TLS;
- поведение при высокой нагрузке;
- резервное копирование и восстановление;
- HTTPS-cookie и Origin-проверка за реальным reverse proxy;
- email-подтверждение, восстановление пароля и MFA;
- реальные периодические HTTP-проверки сайтов и защита от DNS rebinding;
- пагинация списка сайтов.
