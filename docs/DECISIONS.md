# Технические решения

## Проверка новых зависимостей через GitHub

Дата: 2026-09-06

Выбрано:

Перед добавлением новой библиотеки или обязательного внешнего компонента создаётся GitHub issue. В нём фиксируются назначение, рассмотренные варианты, лицензия, влияние на размер/обновления и риски безопасности. Текущий MVP реализован без новых Go-зависимостей сверх уже существующих `pgx` и `x/crypto`.

Для необязательной Docker Compose-установки создан GitHub issue #1 до публикации соответствующего коммита.

## Self-hosted и универсальные проекты

Дата: 2026-09-06

Причина:

Пользователь должен устанавливать Uptime Control на собственный сервер и иметь возможность мониторить не только сайт, но и любой свой проект.

Выбрано:

- основной способ поставки — self-hosted;
- приложение поддерживает URL-префикс через `BASE_PATH`, например `/uptimec`;
- `PUBLIC_ORIGIN` остаётся только origin (`https://igra.ru`), потому что браузер не включает путь в заголовок `Origin`;
- продуктовая сущность `project` является контейнером;
- конкретные HTTP, TCP, heartbeat и agent-проверки являются отдельными `monitors` проекта;
- первым типом monitor остаётся HTTP/HTTPS.

Минусы:

- текущие `sites` и `/api/v1/sites` нужно безопасно перенести на новую модель;
- установка под URL-префиксом требует согласованной конфигурации reverse proxy;
- self-hosted-режиму нужен безопасный bootstrap первого владельца вместо постоянно открытой регистрации.

Что потребуется дальше:

- новая миграция без изменения уже применённых миграций;
- API проектов и monitors;
- запрет открытой регистрации после создания первого владельца либо явная настройка администратора.

## Стандартный HTTP-сервер Go

Дата: 2026-09-05

Причина:

На первом этапе нужны только несколько маршрутов и middleware, поэтому отдельный веб-фреймворк не требуется.

Рассматривались:

- стандартный `net/http`;
- сторонний роутер или полноценный веб-фреймворк.

Выбрано:

Стандартный `net/http`.

Минусы:

Часть удобных механизмов маршрутизации и middleware нужно будет организовать внутри проекта.

## PostgreSQL и pgx

Дата: 2026-09-05

Причина:

Проекту нужны транзакции, связи, индексы и хранение временных рядов на этапе MVP.

Выбрано:

- PostgreSQL как основная база данных;
- `pgx/v5` как Go-драйвер и пул соединений;
- чистый SQL вместо архитектуры вокруг ORM.

Минусы:

- запросы и преобразование данных нужно писать явно;
- таблица проверок потребует отдельной стратегии роста.

Что может потребоваться в будущем:

- секционирование временных рядов;
- отдельное аналитическое хранилище;
- read replicas.

## Миграции при запуске приложения

Дата: 2026-09-05

Причина:

Для раннего MVP нужен простой воспроизводимый запуск без отдельного инструмента. Миграции выполняются в транзакции под advisory lock.

Минусы:

- пользователь БД приложения пока должен иметь права на изменение схемы;
- при сложных production-развёртываниях миграции лучше запускать отдельной командой до старта приложения.

Что может потребоваться в будущем:

Вынести миграции в отдельную команду, когда появятся несколько реплик и отдельные права production-БД.

## Авторизация MVP

Дата: 2026-09-05

Выбрано:

- вход по email и паролю;
- пароль хешируется Argon2id с индивидуальной солью;
- серверная сессия живёт 7 дней;
- случайный 32-байтовый токен передаётся в `HttpOnly`, `SameSite=Lax`, `Secure` cookie;
- в базе хранится только SHA-256-хеш токена;
- у сайта один владелец.

Минусы:

- командный доступ и OAuth потребуют расширения модели позже;
- cookie-сессии требуют HTTPS и защиты изменяющих запросов;
- email-подтверждение и восстановление пароля нужно добавить отдельно.

## Владение и мягкое удаление сайтов

Дата: 2026-09-06

Причина:

Пользователь не должен получить чужой сайт заменой UUID, а случайное удаление не должно уничтожить будущую историю мониторинга.

Выбрано:

- владелец берётся только из действующей серверной сессии;
- запрос к отдельному сайту фильтруется одновременно по `id` и `user_id`;
- чужой сайт скрывается тем же `404`, что и несуществующий;
- DELETE устанавливает `deleted_at` и `enabled=false`;
- DELETE требует `X-Confirm-Delete: true`;
- одинаковый URL можно создать снова после мягкого удаления.

Минусы:

- данные продолжают занимать место;
- позже потребуется административная процедура восстановления и окончательного удаления;
- frontend должен явно добавлять заголовок подтверждения.
