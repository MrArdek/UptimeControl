# Uptime Control

## О проекте

**Uptime Control** — self-hosted-сервис мониторинга проектов, который пользователь устанавливает на собственный сервер.

Приложение может работать на отдельном домене или внутри существующего сайта по пути, например:

```text
https://igra.ru/uptimec
```

Основная сущность продукта — **проект**. Проектом может быть сайт, API, игра, бот, backend-сервис или другое приложение. К проекту подключаются отдельные проверки (**monitors**). Текущая версия поддерживает HTTP/HTTPS, TCP и heartbeat для сервисов без frontend; данные серверного агента появятся на следующем профильном этапе.

Основной API использует модель `projects` + `monitors`. Старые записи `sites`, их проверки и инциденты автоматически переносятся миграцией без удаления данных.

Пользователь создаёт проект и добавляет проверяемые адреса, после чего Uptime Control:

- периодически проверяет доступность сайта;
- проверяет сайт из разных регионов;
- сообщает о падениях и восстановлении;
- собирает статистику посещаемости;
- показывает активных пользователей;
- собирает данные об источниках трафика и поведении пользователей;
- собирает метрики производительности сайта;
- при установке серверного агента собирает метрики самого сервера.

## Состояние MVP

Self-hosted MVP уже включает:

- первого владельца установки и защищённые cookie-сессии;
- проекты с HTTP/HTTPS-, TCP- и heartbeat-monitors;
- периодический планировщик, историю с пагинацией, uptime/coverage и автоматические инциденты;
- Telegram-уведомления о падении и восстановлении;
- постоянную очередь Telegram/webhook с повторными попытками и журналом доставки;
- встроенный Dashboard;
- установку на отдельный monitoring-сервер через Docker Compose или бинарный файл.

Инструкция установки находится в [`docs/SERVER_INSTALL.md`](docs/SERVER_INSTALL.md). Для независимого мониторинга рекомендуется отдельный адрес вроде `uptime.igra.ru`, напрямую указывающий на соседний сервер.

## 1. Мониторинг доступности сайта

Для каждого добавленного сайта система периодически выполняет проверки.

### Что проверяем

- доступен сайт или нет;
- HTTP status code;
- время ответа сервера;
- история проверок;
- время начала падения;
- длительность падения;
- время восстановления.

### Проверки из разных регионов

Система должна уметь проверять один и тот же сайт из нескольких географических регионов.

Например:

- Европа;
- Азия;
- Северная Америка;
- другие регионы по мере развития инфраструктуры.

Для каждой проверки сохраняются:

- регион проверки;
- дата и время;
- доступность;
- HTTP status code;
- response time;
- ошибка, если сайт недоступен.

Это позволяет отличать полное падение сайта от региональной проблемы.

## 2. Web Analytics

Для сбора статистики на сайт пользователя устанавливается JavaScript-трекер Uptime Control.

Пример подключения:

```html
<script src="https://cdn.uptime-control.com/tracker.js"
        data-site-id="SITE_ID"></script>
```

> Точный URL и формат подключения будут определены при реализации.

### Основные показатели

Система должна собирать и показывать:

1. пользователей сейчас на сайте;
2. пользователей за день;
3. пользователей за неделю;
4. пользователей за месяц;
5. количество просмотров страниц;
6. количество запросов;
7. нагрузку по времени;
8. пики нагрузки;
9. среднее время ответа;
10. среднее время загрузки сайта.

### Пользователи

В аналитике отдельно учитываются:

- текущие пользователи онлайн;
- уникальные пользователи;
- сессии;
- просмотры страниц.

## 3. Данные о посетителях

Для каждого посещения система собирает доступные аналитические и технические данные.

### Источник пользователя

Сохраняются:

1. источник перехода;
2. `utm_source`;
3. `utm_campaign`;
4. `utm_medium`;
5. `referrer`;

### Технические данные

Сохраняются:

1. устройство;
2. страна;
3. браузер.

### Поведение пользователя

По включённой пользователем расширенной аналитике система может собирать:

1. страницы, которые посещал пользователь;
2. количество кликов;
3. элементы или ссылки, по которым пользователь кликал;
4. совершённые события;
5. последовательность действий пользователя в рамках сессии.

## 4. Производительность сайта

Система должна хранить метрики производительности во времени.

### Основные метрики

- среднее время ответа сервера;
- среднее время загрузки сайта;
- количество запросов;
- количество запросов по времени;
- пиковые значения нагрузки;
- динамика нагрузки.

Данные должны отображаться на графиках, чтобы пользователь видел изменение показателей по времени.

## 5. Мониторинг сервера

Для получения системных метрик сервера требуется отдельный **Uptime Control Agent**, который пользователь устанавливает на свой VPS или сервер.

JavaScript-трекер в браузере не может получить эти показатели напрямую.

### Метрики сервера

Агент собирает:

1. CPU;
2. RAM;
3. Disk;
4. Load Average;
5. процессы;
6. сетевой трафик.

### CPU

Необходимо сохранять:

- текущую загрузку;
- среднюю загрузку;
- пиковую загрузку;
- историю нагрузки.

### RAM

Необходимо сохранять:

- общий объём;
- используемую память;
- свободную память;
- процент использования.

### Disk

Необходимо сохранять:

- общий объём;
- занятое место;
- свободное место;
- процент заполнения.

### Load Average

Необходимо хранить показатели нагрузки сервера по времени.

### Процессы

Система должна иметь возможность получать информацию о запущенных процессах и их потреблении ресурсов.

### Сетевой трафик

Необходимо собирать:

- входящий трафик;
- исходящий трафик;
- динамику трафика;
- пики.

## 6. Custom Events

Разработчик сайта должен иметь возможность отправлять собственные события в Uptime Control.

### Простое событие

```javascript
uptime.track("signup");
```

### Событие с параметрами

```javascript
uptime.track("purchase", {
    plan: "pro",
    amount: 2990
});
```

### Другие примеры

```javascript
uptime.track("button_click", {
    button: "buy_now"
});
```

```javascript
uptime.track("form_submit", {
    form: "contact"
});
```

```javascript
uptime.track("video_play", {
    video_id: "intro"
});
```

### Требования к событиям

Для каждого события система должна сохранять:

- сайт;
- название события;
- дату и время;
- идентификатор сессии;
- страницу;
- переданные разработчиком параметры;
- связанные UTM-параметры;
- источник пользователя.

## 7. Custom Properties

Разработчик должен иметь возможность передавать собственные параметры пользователя или сессии.

Пример:

```javascript
uptime.identify({
    user_id: "123",
    tariff: "business",
    source: "telegram"
});
```

Custom Properties позволяют владельцу сайта передавать поля, специфичные именно для его проекта.

Например:

- внутренний ID пользователя;
- тариф;
- тип аккаунта;
- категория клиента;
- источник регистрации;
- вариант A/B-теста;
- другие произвольные параметры.

## 12. Технологический стек

Основной язык проекта — **Go**.

### Backend

Используем:

- **Go** — основной backend;
- REST API;
- фоновые задачи;
- обработка мониторинговых проверок;
- обработка событий и метрик;
- уведомления;
- работа с очередями;
- сервисы аналитики.

### Regional Check Nodes

Узлы, которые проверяют сайты из разных регионов, также пишутся на **Go**.

Причины:

- высокая производительность;
- низкое потребление памяти;
- удобная конкурентность;
- простое развёртывание;
- возможность собирать один бинарный файл.

### Server Agent

Server Agent пишется на **Go**.

Он устанавливается на сервер пользователя и собирает:

- CPU;
- RAM;
- Disk;
- Load Average;
- процессы;
- сетевой трафик.

Преимущество Go здесь в том, что агент можно поставлять как один исполняемый файл без необходимости устанавливать дополнительные runtime-зависимости.

### Frontend

Для пользовательского интерфейса используем:

- **TypeScript**;
- React;
- предпочтительно Next.js.

Frontend отвечает за:

- Dashboard;
- графики;
- страницы сайтов;
- инциденты;
- аналитику;
- настройки;
- уведомления;
- управление Server Agent;
- Custom Events;
- Custom Properties.

### JavaScript Tracker

Трекер сайта пишется на **TypeScript**, после чего собирается в минимизированный JavaScript-файл.

Пример подключения:

```html
<script src="https://cdn.uptime-control.com/tracker.js"
        data-site-id="SITE_ID"></script>
```

Tracker должен быть:

- максимально лёгким;
- асинхронным;
- не блокировать загрузку сайта;
- устойчивым к ошибкам;
- минимально влиять на производительность сайта пользователя.

### Database

Основная база данных:

- **PostgreSQL**.

Используется для:

- пользователей;
- проектов;
- сайтов;
- настроек;
- инцидентов;
- мониторинговых проверок;
- конфигурации агентов;
- custom events;
- custom properties;
- системных данных.

### SQL

Для работы с базой используется SQL.

На этапе реализации можно использовать:

- чистый SQL;
- query builder;
- ORM только там, где это действительно упрощает разработку.

Рекомендуемый подход — не строить архитектуру проекта вокруг ORM.

### Хранение временных рядов

Мониторинг и аналитика будут генерировать большое количество временных данных.

К ним относятся:

- uptime checks;
- response time;
- pageviews;
- sessions;
- server metrics;
- CPU;
- RAM;
- network traffic;
- performance metrics.

На первом этапе эти данные можно хранить в PostgreSQL.

При росте нагрузки архитектура должна позволять вынести временные ряды в специализированное хранилище без переписывания основной бизнес-логики.

### Python

**Python не является обязательной частью MVP.**

Его можно добавить позже как отдельный аналитический сервис.

Возможные задачи:

- anomaly detection;
- определение необычных скачков нагрузки;
- прогнозирование нагрузки;
- поиск аномалий CPU/RAM;
- анализ поведения пользователей;
- прогноз возможных проблем;
- ML;
- расширенная статистика.

Пример будущей архитектуры:

```text
Go Backend
    │
    ├── Monitoring
    ├── Analytics API
    ├── Events
    ├── Notifications
    │
    └──────────────► Python Analytics Service
                         │
                         ├── anomaly detection
                         ├── predictions
                         └── ML
```

### Итоговый стек MVP

```text
Backend                Go
Regional Check Nodes   Go
Server Agent           Go

Frontend               TypeScript + React / Next.js
Website Tracker        TypeScript → JavaScript

Database               PostgreSQL
Queries                 SQL

Advanced Analytics     Python — позже
```

### Принцип проекта

Не добавляем новый язык программирования без необходимости.

Каждый дополнительный язык увеличивает:

- сложность разработки;
- стоимость поддержки;
- количество зависимостей;
- сложность CI/CD;
- сложность отладки.

Поэтому основа Uptime Control:

**Go + TypeScript + PostgreSQL.**

Python подключается только тогда, когда для него появляется отдельная аналитическая задача, которую невыгодно реализовывать на Go.
