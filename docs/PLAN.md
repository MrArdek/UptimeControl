# План проекта

Дата актуализации: 2026-09-06

## Главная цель проекта

Создать self-hosted-сервис, который пользователь устанавливает на свой сервер и открывает на отдельном домене или по пути вроде `https://igra.ru/uptimec`. Сервис объединяет мониторинг проектов, веб-аналитику и метрики серверов в одном интерфейсе.

## Предлагаемый MVP

Первая рабочая версия должна позволять владельцу установленного экземпляра создать проект, добавить к нему HTTP/HTTPS-проверку и увидеть текущий статус, время ответа и историю инцидентов.

Проектом может быть сайт, API, игра, бот или другой сервис. В MVP фактически проверяется доступный по HTTP/HTTPS адрес. Другие типы мониторинга подключаются к проекту позднее отдельными monitors.

Веб-аналитику, Server Agent и сложные региональные проверки лучше добавлять после устойчивой работы базового мониторинга.

## Ближайшие задачи

### 1. Уточнить требования MVP

Описание:

- определить обязательные функции первой версии;
- выбрать способ авторизации;
- определить роли пользователей;
- согласовать минимальные параметры проверки сайта и уведомлений.

Зачем:

Это позволит не смешивать в первой реализации мониторинг, аналитику и серверные метрики.

Риски:

- без зафиксированных границ MVP проект может стать слишком большим до появления первой рабочей версии.

Как проверить:

- список функций MVP согласован и отражён в документации.

Статус: **in progress**

Принято:

- self-hosted как основной способ поставки;
- работа на отдельном домене или под URL-префиксом через `BASE_PATH`;
- универсальная модель «проект + проверки», к которой нужно перейти без потери существующих данных;
- PostgreSQL как основная база;
- email и пароль для первого способа входа;
- серверная сессия в защищённой cookie;
- один владелец сайта в MVP.

Остаётся выбрать первый канал уведомлений и безопасный режим создания первого владельца self-hosted-экземпляра.

### 2. Подготовить каркас Go-приложения

Описание:

- выбрать HTTP-роутер и структуру пакетов;
- добавить конфигурацию приложения;
- реализовать корректное завершение сервера;
- добавить endpoint проверки состояния приложения.

Возможные области:

- `main.go`;
- `cmd/`;
- `internal/config/`;
- `internal/http/`.

Риски:

- преждевременное усложнение структуры;
- выбор тяжёлых зависимостей без необходимости.

Как проверить:

- приложение запускается;
- health endpoint возвращает успешный ответ;
- тесты проходят.

Статус: **done**

Результат:

- используется HTTP-сервер из стандартной библиотеки Go;
- добавлены таймауты сервера и корректное завершение;
- реализован `GET /health`;
- добавлены тесты конфигурации и маршрута;
- сборка и тесты проверены на Go 1.27.1.

### 3. Подключить PostgreSQL и миграции

Описание:

- добавить безопасное чтение строки подключения из окружения;
- выбрать инструмент миграций;
- создать начальные таблицы пользователей, сайтов и проверок;
- добавить проверку соединения с базой.

Риски:

- не хранить пароль базы в коде;
- не изменять схему вручную в production;
- заранее продумать рост таблицы результатов проверок.

Как проверить:

- чистая база разворачивается миграциями;
- приложение подключается к ней;
- повторный запуск миграций безопасен.

Статус: **done**

Результат:

- добавлен пул соединений `pgx/v5`;
- `DATABASE_URL` проверяется до запуска;
- миграции применяются транзакционно и защищены advisory lock;
- созданы таблицы `users`, `sessions`, `sites`, `uptime_checks` и `incidents`;
- `GET /ready` проверяет доступность базы;
- чистая база, повторный запуск миграций и запуск сервера проверены на PostgreSQL 18.6.

### 4. Реализовать пользователей и авторизацию

Описание:

- регистрация и вход;
- безопасное хеширование паролей;
- проверка авторизации на backend;
- разделение данных разных пользователей.

Риски:

- способ авторизации должен быть согласован до реализации;
- токены, cookie и пароли нельзя логировать.

Как проверить:

- пользователь видит только собственные сайты;
- неверные учётные данные не дают доступ;
- защищённые маршруты недоступны без авторизации.

Статус: **done**

Результат:

- реализованы регистрация, вход, выход и `/me`;
- пароль хешируется Argon2id;
- cookie имеет `HttpOnly`, `SameSite=Lax` и `Secure` по умолчанию;
- в БД хранится только SHA-256-хеш случайного токена сессии;
- добавлены одинаковая ошибка неверных данных входа, Origin-проверка и rate limit;
- модульные и сквозные проверки с PostgreSQL пройдены.

### 5. Реализовать базовый мониторинг сайтов

Описание:

- добавление и изменение сайта;
- периодические HTTP-проверки;
- сохранение статуса и времени ответа;
- создание и закрытие инцидентов;
- история результатов.

Риски:

- защита от SSRF при запросах к пользовательским URL;
- ограничения времени ответа, размера тела и количества перенаправлений;
- контроль конкурентности и частоты проверок.

Как проверить:

- доступный тестовый сайт получает статус online;
- недоступный сайт получает статус offline;
- падение создаёт один инцидент, а восстановление закрывает его.

Статус: **in progress**

Готово:

- CRUD сайтов;
- обязательная авторизация и проверка владельца в SQL;
- мягкое удаление с явным подтверждением;
- базовая нормализация и блокировка локальных/private URL;
- защита от дубликата активного URL одного владельца.

Осталось:

- добавить новую модель `projects` и `monitors` миграцией с сохранением текущих `sites`;
- заменить временные site-маршруты на API проектов и проверок;
- безопасный HTTP-клиент с повторной проверкой DNS/IP перед соединением;
- планировщик;
- запись результатов в `uptime_checks`;
- открытие и закрытие инцидентов;
- API истории проверок и инцидентов.

### 6. Добавить уведомления и простой Dashboard

Описание:

- показать список сайтов, состояние и историю инцидентов;
- добавить первый канал уведомлений;
- отображать понятные ошибки настройки.

Риски:

- не раскрывать данные одного пользователя другому;
- ограничивать повторные уведомления.

Как проверить:

- пользователь видит актуальное состояние своих сайтов;
- при падении и восстановлении отправляются ожидаемые уведомления.

Статус: **not started**
