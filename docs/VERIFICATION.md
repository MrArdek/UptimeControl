## Проверка с PostgreSQL

Нужна отдельная тестовая или локальная база. Никогда не используйте production-базу для экспериментов.

Задайте переменные окружения без добавления секрета в Git:

```bash
export DATABASE_URL=postgresql://localhost/uptime_control
export HTTP_ADDR=127.0.0.1:8080
export PUBLIC_ORIGIN=http://127.0.0.1:8080
export BASE_PATH=
export SESSION_COOKIE_SECURE=false
go run .
```

В другом терминале:

```bash
curl -i http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/ready
```

Ожидается:

- `/health` возвращает `200` и `{"status":"ok"}`;
- `/ready` возвращает `200` и `{"status":"ready"}`;
- при недоступной БД `/ready` возвращает `503`;
- повторный запуск приложения не применяет одну миграцию дважды;
- `Ctrl+C` корректно завершает собранный сервер.

Успешно проверено:

- `go test ./...`;
- `go test -race ./...`;
- `go vet ./...`;
- `go build`;

- применение `000001_initial_schema.up.sql`;

- применение `000003_projects_and_monitors.up.sql` и наличие `projects` и `monitors`;
- перенос существующего site, его проверки и открытого инцидента без потери данных;
- повторный запуск без повторного применения миграции;
- ответы `/health` и `/ready` со статусом `200`;
- маршруты с `BASE_PATH=/uptimec` доступны только под `/uptimec`, а cookie получает `Path=/uptimec`;
- завершение собранного бинарного файла по `SIGINT` с кодом `0`;
- регистрация пользователя со статусом `201`;
- вторая регистрация после создания владельца отклоняется со статусом `403`;
- нормализация email к нижнему регистру;
- получение пользователя через cookie со статусом `200`;
- отзыв сессии при logout и последующий `401`;
- повторный вход со статусом `200`;
- Argon2id-хеш вместо пароля и 32-байтовый хеш токена в PostgreSQL;
- единая ошибка неверных учётных данных;
- отклонение чужого Origin со статусом `403`;
- ограничение попыток входа со статусом `429`;
- создание HTTP- и heartbeat-проектов владельцем со статусом `201`;
- список проектов и отображение monitors со статусом `200`;
- Dashboard открывается под `/uptimec`, вход и список проектов проверены в браузере;
- блокировка literal private URL со статусом `400`;
- DNS/IP-проверка блокирует private-адрес перед соединением;
- реальная периодическая HTTP-проверка публичного адреса;
- HTTP `404` открывает инцидент, последующий успешный ответ закрывает его;
- heartbeat возвращает `204` и записывается как успешная проверка;
- пропущенный heartbeat открывает инцидент, следующий сигнал закрывает его;
- в БД находится только 32-байтовый SHA-256-хеш heartbeat-токена;
- применение `000004_project_webhooks.up.sql` и наличие `project_webhooks` и `webhook_deliveries`;
- создание webhook владельцем со статусом `201`, секрет присутствует только в этом ответе;
- список webhooks со статусом `200` без секретов;
- невалидные события отклоняются со статусом `400`, шестой webhook — со статусом `409`;
- удаление webhook без подтверждения — `400`, с подтверждением — `204`;
- диспетчер доставляет подписанный payload (`X-UptimeControl-Signature`) и пропускает неподписанные события;
- недоступный получатель повторяется до 3 попыток, исход пишется в `webhook_deliveries`;
- private URL webhook отклоняется до установки соединения;
- Telegram-уведомления продолжают работать рядом с webhooks без изменений.

Проверки выполнялись только во временных локальных базах. После проверки обе базы удалены, локальный PostgreSQL остановлен. Реальные пользовательские данные не создавались и не удалялись.

## Пока не проверено

- запуск на удалённом Linux-сервере;
- сборка Docker-образа: команда Docker отсутствует в текущем окружении;
- работа за reverse proxy и TLS;
- поведение при высокой нагрузке;
- резервное копирование и восстановление;
- HTTPS-cookie и Origin-проверка за реальным reverse proxy;
- email-подтверждение, восстановление пароля и MFA;
- реальная доставка Telegram: нужны тестовые `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`;
- сквозная доставка webhook на внешний URL из production-подобной сети (юнит-покрытие использует стабы, т.к. SSRF-защита режет loopback);
- пагинация списка проектов.
