# Резервное копирование

Дата актуализации: 2026-09-06

## Текущее состояние

Проект использует PostgreSQL и уже содержит начальную схему, но реальных пользовательских данных пока нет. Исходный код хранится в Git-репозитории. Автоматические резервные копии не настроены.

## Что нужно сохранять

После появления production-инфраструктуры в резервные копии должны входить:

- база данных PostgreSQL;
- конфигурация инфраструктуры без секретов;
- загруженные пользователями файлы, если такая функция появится;
- миграции базы данных;
- важные настройки уведомлений и мониторинга.

Исходный код должен сохраняться через удалённый Git-репозиторий, но Git не заменяет резервное копирование пользовательских данных.

Мягко удалённые сайты остаются в PostgreSQL и попадут в бэкап. Это позволяет восстановить ошибочно удалённую запись административной процедурой, которой пока нет в публичном API.

## Что нельзя помещать в обычный бэкап проекта

- открытые пароли;
- API-ключи;
- приватные ключи;
- незашифрованные токены;
- локальный `.env` в Git-репозитории.

Если секреты необходимы для аварийного восстановления, они должны храниться отдельно в защищённом менеджере секретов.

## План резервного копирования PostgreSQL

После подключения базы данных необходимо:

1. Настроить автоматический ежедневный бэкап.
2. Шифровать резервные копии при хранении и передаче.
3. Хранить копии отдельно от основного сервера и базы.
4. Настроить срок хранения и удаление устаревших копий.
5. Ограничить доступ к копиям.
6. Регулярно проверять восстановление на отдельном окружении.

Рекомендуемая начальная политика хранения должна быть уточнена перед production-запуском. Например: ежедневные копии за 14 дней и ежемесячные копии за 6 месяцев.

## Проверка восстановления

Бэкап нельзя считать рабочим, пока не выполнено тестовое восстановление.

Минимальная проверка:

1. Создать отдельную пустую базу.
2. Восстановить последнюю резервную копию.
3. Запустить миграции в режиме проверки.
4. Проверить количество основных записей и связи.
5. Запустить приложение против восстановленной базы.
6. Зафиксировать дату, длительность и результат проверки.

## Ответственные решения до production

- выбрать место хранения резервных копий;
- определить RPO — допустимый объём потерянных данных;
- определить RTO — допустимое время восстановления;
- определить срок хранения копий;
- назначить ответственного за регулярную проверку восстановления.
