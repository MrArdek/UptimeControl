# База данных

Дата актуализации: 2026-09-06

## Технология

- PostgreSQL 14 или новее.
- Локальная интеграционная проверка выполнена на PostgreSQL 18.6.
- Подключение из Go выполняется через `github.com/jackc/pgx/v5/pgxpool`.
- Строка подключения передаётся только через `DATABASE_URL`.

## Миграции

SQL-файлы находятся в `internal/migrations/sql` и встраиваются в бинарный файл при сборке.

При запуске приложение:

1. Подключается к PostgreSQL.
2. Открывает транзакцию.
3. Получает PostgreSQL advisory lock.
4. Создаёт `schema_migrations`, если таблицы ещё нет.
5. Применяет новые `*.up.sql` в порядке имён.
6. Записывает выполненную версию.
7. Фиксирует всю транзакцию.

Повторный запуск пропускает уже применённые миграции.

Применённые миграции нельзя редактировать. Изменение схемы оформляется новым файлом с возрастающим номером.

## Запланированная модель полного продукта

Полный контракт сущностей, времени, дедупликации, агрегации и retention находится в [DATA_CONTRACTS.md](DATA_CONTRACTS.md). Ниже перечислена целевая модель; эти таблицы ещё не реализованы и будут добавляться только новыми миграциями соответствующих этапов.

| Область | Планируемые таблицы | Ключевые ограничения |
|---|---|---|
| Региональные проверки | `check_nodes`, `monitor_assignments`; `uptime_checks` получает node/region/result ID | уникальный `(node_id, result_id)`, узел пишет только назначенные monitors |
| Web Analytics | `analytics_sources`, `analytics_visitors`, `analytics_sessions`, `analytics_events` | уникальный `(analytics_source_id, event_id)`, публичный ключ не разрешает чтение |
| Серверы | `servers`, `server_agents`, `server_metric_samples` | уникальный `(agent_id, sample_id)`, credential привязан к одному server |
| Агрегаты | отдельные минутные, часовые и дневные таблицы monitoring/analytics/performance/server | уникальный `(subject_id, metric, bucket_start)`, UTC buckets, `sum/count/min/max` |
| Приём и обслуживание | `ingest_rejections`, задания пересчёта и очистки | без исходного payload и секретов, ограниченный срок хранения |

Таблицы конфигурации связаны с `projects` через `ON DELETE RESTRICT` и мягкое удаление. Большие raw-таблицы проектируются с индексом/секционированием по времени и project/source ID после измерения запросов; физическое секционирование не вводится заранее. Существующие `uptime_checks` и `incidents` мигрируются без потери данных.

Store-интерфейсы должны разделять конфигурацию, raw ingest, агрегацию и отчёты. HTTP- и бизнес-слои не должны зависеть от конкретной схемы секционирования или будущего внешнего хранилища.

### Общие типы и единицы

- серверные ID — UUID v4; `BIGINT GENERATED ... AS IDENTITY` допустим только для внутреннего журнала доставки;
- времена событий и получения — `TIMESTAMPTZ`, UTC;
- длительность — целое число миллисекунд; размеры/счётчики — `BIGINT` в байтах; проценты — конечное число от 0 до 100;
- country — два символа ISO 3166-1 alpha-2 либо `unknown`;
- properties — валидированный ограниченный JSON, который нельзя индексировать или превращать в labels без явного решения;
- отсутствующее измерение хранится как `NULL`, подтверждённый ноль — как `0`.

### Агрегация и сроки хранения

Начальные сроки: raw uptime 90 дней; raw analytics, browser performance и server metrics 30 дней; минутные агрегаты 90 дней; часовые 24 месяца; дневные до удаления проекта. Incidents и конфигурация хранятся до удаления проекта. Очистка raw выполняется только после фиксации покрывающего агрегата, небольшими пакетами.

Среднее агрегируется через `sum` и `count`; peak — через `max`; unique за длинный период нельзя получать суммой дневных distinct. Для точного v1-отчёта unique вычисляется по идентификаторам доступного периода; переход на mergeable sketch требует отдельного решения и проверки погрешности.

## Таблицы

### `users`

Учётные записи пользователей.

- UUID создаётся приложением.
- Email уникален без учёта регистра среди неудалённых записей.
- Хранится только хеш пароля.
- `deleted_at` предназначен для мягкого удаления.
- Частичный уникальный индекс запрещает два одинаковых активных URL у одного пользователя.

### `sessions`

Серверные пользовательские сессии.

- В базе хранится хеш токена, а не исходный токен.
- Сессия имеет срок действия и может быть отозвана.
- Сессии связаны с пользователем.
- Токен хешируется SHA-256 и передаётся клиенту только через cookie.

### `sites`

Устаревшая таблица HTTP-целей. Она сохраняется для безопасного перехода, но новая логика записывает данные в `projects` и `monitors`.

- Каждый сайт связан ровно с одним пользователем.
- Интервал проверки ограничен диапазоном от 30 секунд до 24 часов.
- `deleted_at` предназначен для мягкого удаления.

### `uptime_checks`

Временной ряд результатов проверок сайта.

- Хранит регион, время, доступность, HTTP-статус, время ответа и безопасное описание ошибки.
- Каждая запись связана с `monitors.id` через `monitor_id`.
- Основной индекс оптимизирует историю одного monitor от новых записей к старым.

### `incidents`

Периоды недоступности сайта.

- `resolved_at IS NULL` означает открытый инцидент.
- Частичный уникальный индекс разрешает только один открытый инцидент на monitor.

### `projects`

Универсальные проекты владельца: сайт, API, игра, бот или другой сервис.

- Проект принадлежит одному владельцу self-hosted-экземпляра.
- У проекта есть название, описание и несколько monitors.
- Удаление мягкое через `deleted_at`.

### `monitors`

Конкретные способы проверки проекта.

- `http` выполняет безопасный HTTP/HTTPS-запрос;
- `heartbeat` ожидает входящий сигнал от бота, cron или worker;
- `next_check_at` используется планировщиком и одновременно предотвращает повторный захват задания;
- последние состояние, HTTP-код, время ответа и безопасная ошибка хранятся для Dashboard;
- heartbeat-токен хранится только как SHA-256-хеш;
- таймаут HTTP ограничен 1–30 секундами, интервал — 30 секунд–24 часа.

### `project_webhooks`

Исходящие notification-эндпоинты проекта (миграция `000004`).

- Каждый webhook принадлежит проекту; доступ владельца проверяется через `projects.user_id`.
- `url` — публичный HTTP/HTTPS-адрес получателя; SSRF-проверка повторяется при каждой доставке.
- `secret` — сырой 32-байтовый HMAC-секрет для подписи payload; показывается владельцу один раз при создании, в `GET` не возвращается, в логи не пишется.
- `events` — каноническое подмножество `down,recovered`.
- Удаление мягкое через `deleted_at` + `enabled=false`; один проект ограничен 5 активными webhooks на уровне сервиса.

### `webhook_deliveries`

Журнал исхода каждой доставки (append-only).

- `webhook_id` ссылается на `project_webhooks.id` через `ON DELETE CASCADE`.
- Хранит событие, HTTP-статус получателя, число попыток и безопасный текст ошибки без URL и секрета.

### `schema_migrations`

Служебный список уже применённых миграций.

## Связи и удаление

- `sites.user_id` ссылается на `users.id` через `ON DELETE RESTRICT`.
- Проверки и инциденты защищены от каскадного удаления monitor.
- Сессии удаляются вместе с физически удаляемой записью пользователя.
- В прикладном API удаление пользователя и сайта должно быть мягким и требовать подтверждения.
- Реализованное удаление сайта устанавливает `deleted_at`, выключает проверку и не удаляет историю.

## Масштабирование

`uptime_checks` станет самой быстрорастущей таблицей. До существенной нагрузки нужно определить срок хранения данных, агрегацию старых значений и необходимость секционирования таблицы.

## Миграция старых sites

`000003_projects_and_monitors.up.sql` переносит каждый существующий `site` в проект с одним HTTP monitor. UUID повторно используется в разных таблицах, благодаря чему история проверок и инцидентов перепривязывается без потери данных.
