# Контракты данных и метрик

Дата актуализации: 2026-09-06

Этот документ задаёт общий смысл будущих данных Uptime Control до реализации региональных узлов, Web Analytics и Server Agent. Он не утверждает, что соответствующие API и таблицы уже существуют. Фактические маршруты перечислены в `API.md`, реализованные таблицы — в `DATABASE.md`.

## Связи и границы доступа

```text
user
└── project
    ├── monitor
    │   └── check result ── region node (необязательно)
    ├── analytics source
    │   ├── visitor
    │   ├── session
    │   └── event/pageview/performance sample
    └── server
        └── agent ── server metric sample
```

- `project` — граница владения и изоляции данных. Любое чтение владельцем фильтруется одновременно по `user_id` и `project_id`.
- `monitor` описывает HTTP/HTTPS, TCP или heartbeat-проверку. Региональный узел выполняет только выданные ему задания и не получает доступ к проекту или базе данных.
- `analytics source` выдаёт публичный ключ записи для одного проекта и список разрешённых origin. Этот ключ не даёт права читать аналитику.
- `server` представляет контролируемую машину. У каждого агента отдельный отзываемый секрет записи; агент не может читать проект или писать метрики другого сервера.
- Внешние сборщики работают только через версионированные HTTP API. Прямой доступ узлов, трекеров и агентов к PostgreSQL запрещён.

Идентификаторы серверных сущностей — UUID v4. Клиентское поле `event_id`/`sample_id` — UUID, созданный отправителем для безопасного повтора. Идентификаторы уникальны только внутри соответствующего источника, узла или агента.

## Время и версия протокола

- В JSON время передаётся в UTC в формате RFC 3339 с суффиксом `Z`; PostgreSQL хранит его в `TIMESTAMPTZ`.
- `occurred_at`/`collected_at` — время у источника. `received_at` — время backend и источник истины для приёма, retention и расследования рассинхронизации часов.
- Отчётный часовой пояс — настройка проекта, по умолчанию `UTC`, в формате IANA, например `Europe/Berlin`. Сырые значения не пересчитываются при его смене; меняются только границы отображаемых календарных периодов.
- Backend принимает текущую основную версию `v1`. Каждый batch содержит `schema_version: 1`; неизвестная обязательная версия получает `422 unsupported_schema`.
- Событие из будущего более чем на 5 минут получает `422 invalid_timestamp`. Данные старше срока сырого хранения получают `422 event_too_old`. Остальные запоздалые события принимаются и помечают затронутые агрегаты для пересчёта.
- Рассинхронизация времени узла или агента более 60 секунд отображается как предупреждение. Для состояния online и свежести сервера backend использует `received_at`, чтобы неверные часы источника не показывали ложную доступность.

## Дедупликация и доставка

- Monitoring result уникален по `(node_id, result_id)`; локальная проверка backend использует сгенерированный сервером `result_id`.
- Analytics event уникален по `(analytics_source_id, event_id)`.
- Server sample уникален по `(agent_id, sample_id)`.
- Повтор элемента с тем же ID и тем же содержимым считается успешным и не меняет агрегаты. Тот же ID с другим содержимым получает `409 id_conflict`.
- Batch обрабатывается поэлементно в одной транзакции. Ответ содержит `accepted`, `duplicate` и отклонённые элементы с ID и кодом ошибки; валидные элементы не теряются из-за одного невалидного.
- Семантика отправки — «как минимум один раз» с идемпотентным приёмом. Отправитель удаляет локальную копию только после ответа, где элемент отмечен принятым или дубликатом.

## Определения продуктовых метрик

### Мониторинг

- Наблюдение — один завершённый результат проверки одного monitor из одного региона. Отсутствие наблюдения не считается успешной или неуспешной проверкой.
- Monitor имеет состояние `unknown` до первого актуального наблюдения, `up`, `down`, `paused` или `stale`. Отключённый monitor — `paused`; потеря регионального узла — `stale`, а не `down`.
- Uptime за период = `available_duration / observed_duration × 100%`. Длительности строятся между последовательными изменениями состояния и обрезаются границами периода. `unknown`, `paused`, `stale` и интервалы без наблюдений исключаются из знаменателя и показываются как неполное покрытие.
- Coverage = `observed_duration / report_period_duration × 100%`. Uptime всегда показывается вместе с coverage.
- HTTP status code существует только у HTTP/HTTPS-наблюдения. Heartbeat и TCP хранят `null`.
- Response time monitor измеряется от начала подключения/HTTP-запроса до завершения принятого ответа и хранится в целых миллисекундах. Для неуспешной проверки значение допускается, если измерение было получено до ошибки.
- Общий региональный статус задаётся этапом 12 после выбора кворума; до этого результаты регионов нельзя автоматически сворачивать в глобальный инцидент.

### Посетители и сессии

- Pageview — явное событие загрузки документа или клиентской навигации SPA. Повторный callback одной навигации с тем же `event_id` не создаёт второй pageview.
- Visitor — псевдонимный случайный ID конкретного браузерного профиля внутри одного analytics source. Он не является человеком и не связывается между проектами или устройствами.
- Unique visitors за период — число различных visitor ID среди принятых событий периода. Недельные и месячные unique считаются из набора периода или mergeable sketch после отдельного решения, но никогда не суммой дневных unique.
- Session начинается с первого события visitor. Новая session создаётся после 30 минут без активности или при явном `uptime.reset()`; несколько вкладок одного browser profile используют один visitor ID, но разделяют активность через общий session ID, когда браузерное хранилище доступно.
- Online users — различные session ID, для которых backend получил событие активности за последние 5 минут и не получил явное завершение. Показатель приблизительный и не обещает число физических людей.
- Users for day/week/month — unique visitors в календарных границах часового пояса проекта. Смена часового пояса пересчитывает отчёт, но не переписывает события.
- Referrer и UTM фиксируются при начале сессии. Атрибуция по умолчанию — first touch этой сессии. Пустой referrer без UTM относится к `direct`; отсутствующие или удалённые данные — `unknown`.

### Средние, пики и производительность

- Среднее хранится как `sum / count`, а агрегат хранит оба компонента. Средние разных интервалов объединяются суммированием `sum` и `count`, не средним от средних.
- Peak — максимальное наблюдаемое значение внутри интервала. При укрупнении интервалов берётся максимум дочерних пиков.
- Request count и rate хранятся раздельно: rate = `count / observed_seconds`. Пустой интервал обозначает отсутствие данных, а подтверждённый нулевой счётчик — ноль.
- `monitor_response_time_ms` — синтетическая внешняя проверка.
- `browser_page_load_ms` и браузерные составляющие — измерения Navigation Timing посетителя.
- `application_response_time_ms` и `application_request_count` поступают из серверной интеграции или поддержанного источника агента.
- `browser_resource_count` — ресурсы, видимые браузерному Performance API. Он не равен числу запросов приложения.
- Метрики трёх источников никогда не суммируются и всегда возвращаются с полем `metric_source`.
- Серверные величины используют проценты `0..100`, байты, байты/секунду, секунды и системные load average 1/5/15. Отрицательные значения и `NaN` запрещены; пропуск не заменяется нулём.

## Публичные контракты сбора v1

Все маршруты учитывают `BASE_PATH`. Максимальный HTTP body сбора — 256 КиБ в несжатом виде, максимум 100 элементов в batch. Клиенту следует отправлять batch не реже 10 секунд; backend может вернуть `413 payload_too_large` или `429 rate_limited` с `Retry-After`.

### Monitoring API

Планируемый маршрут: `POST /api/v1/ingest/monitoring/results`.

Авторизация: `Authorization: Bearer <node-secret>`. Один batch относится к одному региональному узлу. Элемент содержит `result_id`, `assignment_id`, `monitor_id`, `region`, `started_at`, `finished_at`, `available`, необязательные `status_code`, `response_time_ms` и нормализованный `error_code`. Произвольный текст сетевой ошибки не принимается как метка высокой кардинальности.

### Analytics API

Планируемый маршрут: `POST /api/v1/ingest/analytics/events`.

Авторизация: публичный ключ источника в теле или заголовке `X-Uptime-Source`. Элемент содержит `event_id`, `occurred_at`, `type`, `visitor_id`, `session_id`, очищенный `page`, атрибуцию, технические поля и ограниченные properties. Endpoint не принимает cookies Dashboard и не возвращает данные проекта.

### Metrics API

Планируемый маршрут: `POST /api/v1/ingest/server/metrics`.

Авторизация: `Authorization: Bearer <agent-secret>`. Один batch относится к одному агенту. Элемент содержит `sample_id`, `collected_at`, CPU/RAM/Disk/Load/Network и, если включено владельцем, ограниченный top процессов. Credentials определяют `server_id`; клиент не может выбрать другой сервер в body.

### Ответ batch

```json
{
  "accepted": 1,
  "duplicate": 1,
  "rejected": [
    {"id": "00000000-0000-4000-8000-000000000003", "code": "invalid_timestamp"}
  ],
  "server_time": "2026-09-06T12:00:00Z"
}
```

Ошибки запроса целиком: `400 invalid_request`, `401 invalid_credentials`, `413 payload_too_large`, `415 unsupported_media_type`, `422 unsupported_schema`, `429 rate_limited`, `503 ingest_unavailable`. Детали не раскрывают существование проекта, узла, источника или агента.

## Контракты чтения и пагинация

- Все новые списки используют cursor pagination: `limit` от 1 до 500, по умолчанию 100; `cursor` — непрозрачная base64url-строка, привязанная к фильтрам и сортировке.
- Ответ содержит массив соответствующего типа и `next_cursor`; `null` означает конец списка. Основная сортировка временных рядов — `(occurred_at DESC, id DESC)`.
- Фильтры времени: `from` включительно, `to` исключительно, RFC 3339. Максимальный диапазон сырого API — 31 день; более длинные периоды обслуживаются агрегатами.
- Неверный или не соответствующий фильтрам cursor получает `400 invalid_cursor`. Удалённые между страницами записи не возвращаются; новые записи могут появиться только при новом проходе с первой страницы.
- Ответ отчёта содержит `timezone`, `from`, `to`, `granularity`, `coverage` и series. Точка без данных имеет `value: null`; подтверждённый ноль имеет `value: 0`.

## Ограничения схемы и кардинальности

- Имена событий и properties: 1–64 ASCII-символа из `[A-Za-z0-9_.-]`; максимум 32 properties на событие/identify.
- Строковое значение property — максимум 256 UTF-8 символов; допустимы строка, конечное число, boolean и `null`. Вложенные объекты и массивы v1 не принимаются.
- Очищенный URL страницы — максимум 2048 байт, без fragment и по умолчанию без query. Владелец может разрешить отдельные имена query-параметров; значения параметров из denylist (`token`, `key`, `secret`, `password`, `code`) не собираются.
- Referrer хранится как origin + path без userinfo, fragment и query. UTM — максимум 256 символов каждое.
- Ошибки, hostname, browser/device/country и имена процессов нормализуются в ограниченные поля. Произвольные строки не используются как labels агрегатов.
- Лимит новых имён custom events — 500 на проект в сутки, новых ключей properties — 100 на проект всего. Превышение отклоняется с `429 cardinality_limit`.

## Хранение, агрегация и удаление

Начальное хранилище — PostgreSQL. Будущие store-интерфейсы разделяются на конфигурацию, raw ingest, агрегацию и отчёты, чтобы физическое хранилище временных рядов можно было заменить без изменения HTTP-контрактов.

| Данные | Сырые данные | Минутные агрегаты | Часовые агрегаты | Дневные агрегаты |
|---|---:|---:|---:|---:|
| Uptime checks | 90 дней | 90 дней | 24 месяца | до удаления проекта |
| Analytics events/pageviews | 30 дней | 90 дней | 24 месяца | до удаления проекта |
| Browser performance | 30 дней | 90 дней | 24 месяца | до удаления проекта |
| Server metrics | 30 дней | 90 дней | 24 месяца | до удаления проекта |
| Ingest rejection audit без payload | 14 дней | не применяется | не применяется | не применяется |

- Incidents, конфигурация и журнал изменения credentials хранятся до удаления проекта. Сырые секреты не хранятся.
- Агрегат имеет `bucket_start`, `timezone=UTC`, `sum`, `count`, `min`, `max` и специфичные счётчики. Минутные buckets строятся из raw, часовые из минутных, дневные из часовых; пересчёт идемпотентен.
- Очистка идёт небольшими пакетами после успешной агрегации. Удаление raw не запускается, пока покрывающий агрегат не зафиксирован.
- Удаление проекта сначала прекращает ingest и отзывает credentials, затем фоново удаляет/анонимизирует связанные raw и агрегаты. Целевой срок удаления — 24 часа; резервные копии истекают по собственной политике.
- Значения retention настраиваются владельцем только в пределах, не превышающих доступный диск; изменение срока вперёд не восстанавливает уже удалённые данные.

## Приватность и границы доверия

- Tracker по умолчанию собирает минимальную аналитику. Автоматические клики, последовательности действий, server request integration, top процессов и расширенные properties включаются владельцем отдельно.
- Не собираются содержимое форм, текст страницы, пароли, cookies сайта, `Authorization`, полные IP-адреса, environment и аргументы команд процессов.
- IP используется в памяти для сетевой обработки, rate limit и определения страны при настроенной GeoIP-базе. В raw analytics IP не сохраняется. Страна хранится как ISO 3166-1 alpha-2 или `unknown`.
- Visitor ID случайный и ограничен одним источником аналитики. `uptime.identify.user_id` считается псевдонимным ID проекта и не связывается между проектами.
- CORS/Origin снижает случайное злоупотребление публичным analytics endpoint, но не доказывает подлинность браузерного события. Analytics показывается как клиентская телеметрия, а не доверенный аудит.
- Node и agent secrets хранятся в БД только как SHA-256-хеши, показываются один раз, передаются только по HTTPS и никогда не попадают в URL или логи.

## Базовый профиль нагрузки полного релиза

Профиль задаёт цель проверки этапа 19 для одной реплики backend и PostgreSQL на одном Linux-сервере с 4 vCPU, 8 ГиБ RAM и SSD. Это цель, а не подтверждённая производительность.

| Показатель | Бюджет |
|---|---:|
| Активные проекты | 100 |
| Monitors | 1 000 |
| Регионов на monitor | до 5 |
| Минимальный интервал региональной проверки | 30 секунд |
| Analytics ingest | 100 событий/с постоянно, 500 событий/с до 60 секунд |
| Server Agents | 100, интервал 30 секунд |
| Размер batch | до 100 элементов / 256 КиБ |
| Одновременные Dashboard/SSE-сессии | 50 |
| Хранилище приложения | предупреждение при 80%, остановка необязательного ingest при 95% доступной квоты |

Целевые задержки при заполненной базе в пределах retention: ingest p95 ≤ 500 мс и p99 ≤ 1 с; API текущего состояния p95 ≤ 500 мс; агрегированный Dashboard за 30 дней p95 ≤ 2 с. Доля ответов 5xx приложения под профилем ≤ 0,1%; очередь агрегации отстаёт не более чем на 2 минуты.

Если профиль не достигается, сначала измеряются запросы, индексы, batching, секционирование и настройки PostgreSQL. Внешнее хранилище или новый runtime добавляются только после отдельного решения. До проверки проект не заявляет эти цифры как production-гарантию.

## Контрольный набор для будущих тестов

В часовом поясе `Europe/Berlin` события visitor `A` происходят в `2026-09-06T21:58:00Z` и `22:02:00Z`, visitor `B` — в `22:03:00Z`; второе событие `B` повторяется с тем же `event_id`. Для отчётного дня 7 сентября ожидаются 2 unique visitors, 2 принятых события и 1 duplicate; событие `A` до 22:00Z относится к 6 сентября. Сумма дневных unique двух дней равна 3, но unique за объединённый период равен 2.

Проверки monitor: `up` в 12:00, `down` в 12:05, `up` в 12:10 и затем отсутствие данных до 12:20. При границе актуальности 5 минут наблюдаемы 15 минут, доступны 10 минут: uptime `66,67%`, coverage `75%`; последние 5 минут — `stale` и не считаются `down`.

Две группы response time: 10 запросов со средним 100 мс и 90 со средним 300 мс. Общее среднее равно 280 мс, а не 200 мс. Пики групп 250 и 900 мс дают общий пик 900 мс. Повтор sample с тем же ID не меняет `sum`, `count` и peak.

Пропущенная точка временного ряда возвращается как `null`; явный серверный счётчик без запросов возвращается как `0`. Эти случаи должны отличаться в API и Dashboard.
