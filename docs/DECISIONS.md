# Технические решения

## Стандартный HTTP-сервер Go

Дата: 2026-09-05

Причина:

На первом этапе нужны только несколько маршрутов и middleware, поэтому отдельный веб-фреймворк не требуется.

Рассматривались:

- стандартный `net/http`;
- сторонний роутер или полноценный веб-фреймворк.

Выбрано:

Стандартный `net/http`.

Минусы:

Часть удобных механизмов маршрутизации и middleware нужно будет организовать внутри проекта.

## PostgreSQL и pgx

Дата: 2026-09-05

Причина:

Проекту нужны транзакции, связи, индексы и хранение временных рядов на этапе MVP.

Выбрано:

- PostgreSQL как основная база данных;
- `pgx/v5` как Go-драйвер и пул соединений;
- чистый SQL вместо архитектуры вокруг ORM.

Минусы:

- запросы и преобразование данных нужно писать явно;
- таблица проверок потребует отдельной стратегии роста.

Что может потребоваться в будущем:

- секционирование временных рядов;
- отдельное аналитическое хранилище;
- read replicas.

## Миграции при запуске приложения

Дата: 2026-09-05

Причина:

Для раннего MVP нужен простой воспроизводимый запуск без отдельного инструмента. Миграции выполняются в транзакции под advisory lock.

Минусы:

- пользователь БД приложения пока должен иметь права на изменение схемы;
- при сложных production-развёртываниях миграции лучше запускать отдельной командой до старта приложения.

Что может потребоваться в будущем:

Вынести миграции в отдельную команду, когда появятся несколько реплик и отдельные права production-БД.

## Авторизация MVP

Дата: 2026-09-05

Выбрано:

- вход по email и паролю;
- пароль хешируется Argon2id с индивидуальной солью;
- серверная сессия живёт 7 дней;
- случайный 32-байтовый токен передаётся в `HttpOnly`, `SameSite=Lax`, `Secure` cookie;
- в базе хранится только SHA-256-хеш токена;
- у сайта один владелец.

Минусы:

- командный доступ и OAuth потребуют расширения модели позже;
- cookie-сессии требуют HTTPS и защиты изменяющих запросов;
- email-подтверждение и восстановление пароля нужно добавить отдельно.
