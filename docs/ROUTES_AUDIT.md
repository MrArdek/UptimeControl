# Аудит маршрутов и ролей

Дата актуализации: 2026-09-06

## Текущее состояние

В проекте есть служебные маршруты и API авторизации. Реализована роль авторизованного пользователя; административной роли пока нет.

Папка `api/v1/ui` существует, но файл `analytics.go` не содержит endpoint или обработчик HTTP-запроса.

## Реализованные маршруты

| Метод | Путь | Назначение | Доступ | Проверки |
| --- | --- | --- | --- | --- |
| GET | `/health` | Проверка работы процесса | Публичный | Другие методы получают `405`; ответ не содержит внутренних данных |
| GET | `/ready` | Проверка готовности приложения и PostgreSQL | Публичный | Таймаут проверки БД — 2 секунды; ошибка скрыта; другие методы получают `405` |
| POST | `/api/v1/auth/register` | Регистрация и создание сессии | Публичный | JSON до 16 КиБ, пароль 12–128 байт, Origin, 5 запросов/мин на IP |
| POST | `/api/v1/auth/login` | Вход и создание сессии | Публичный | Одинаковая ошибка для email/пароля, Origin, 10 запросов/мин на IP |
| POST | `/api/v1/auth/logout` | Отзыв текущей сессии | Пользователь | Cookie-сессия и Origin; cookie удаляется |
| GET | `/api/v1/auth/me` | Текущий пользователь | Пользователь | Только действующая неотозванная cookie-сессия |
| GET | `/api/v1/sites` | До 100 активных сайтов | Пользователь | Фильтр по `user_id` из сессии |
| POST | `/api/v1/sites` | Создание сайта | Пользователь | Владелец из сессии, JSON/Origin, проверка URL |
| GET | `/api/v1/sites/{siteID}` | Просмотр сайта | Владелец | `id` и `user_id` проверяются одним SQL-запросом |
| PATCH | `/api/v1/sites/{siteID}` | Изменение сайта | Владелец | `id` и `user_id`, JSON/Origin, повторная валидация |
| DELETE | `/api/v1/sites/{siteID}` | Мягкое удаление | Владелец | `id` и `user_id`, Origin, `X-Confirm-Delete: true` |

## Реализованные роли

- Неавторизованный посетитель.
- Авторизованный пользователь.

## Предварительная модель доступа

Пользовательская часть модели реализована. Администраторская часть остаётся предложением.

### Неавторизованный посетитель

- регистрация;
- вход;
- health endpoint без внутренних диагностических данных.

### Пользователь

- просмотр и изменение только собственных сайтов;
- просмотр собственных проверок и инцидентов;
- управление собственными настройками уведомлений;
- просмотр собственной аналитики и метрик после появления этих функций.

### Администратор системы

- системная диагностика;
- управление служебными настройками;
- действия поддержки только через явно защищённые маршруты с аудитом.

Администраторская роль не должна автоматически использоваться для обычных пользовательских операций.

## Обязательные проверки для каждого защищённого маршрута

- Авторизация проверяется на backend.
- Доступ проверяется по владельцу ресурса, а не только по наличию входа.
- Идентификаторы из URL не считаются доказательством доступа.
- Входные данные валидируются и имеют ограничения размера.
- Ошибки не раскрывают секреты, SQL и внутреннюю структуру приложения.
- Изменяющие и административные действия журналируются без токенов и паролей.
- Для публичных и дорогих операций применяется ограничение частоты запросов.

## Риски, которые нужно проверить при реализации

- IDOR: доступ к чужому сайту через замену `siteID`.
- SSRF: запросы мониторинга к локальным и служебным сетевым адресам.
- Brute force на маршруте входа.
- Массовое создание сайтов и заданий проверки.
- Утечка диагностической информации через health endpoint и ошибки.
- Небезопасное удаление сайтов и связанных данных.

## Правило обновления документа

После добавления или изменения маршрута нужно зафиксировать здесь метод, путь, назначение, требуемую роль и проверку владельца. Когда появится реальное API, подробные форматы запросов и ответов следует вынести в `docs/API.md`.
