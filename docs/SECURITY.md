# Безопасность проекта

Дата актуализации: 2026-09-10

## Будущие сборщики и приватность

Контракты региональных узлов, JavaScript Tracker и Server Agent описаны в [DATA_CONTRACTS.md](DATA_CONTRACTS.md). До их реализации обязательны следующие границы:

- публичный analytics source key даёт только ограниченное право записи и не является секретом или разрешением чтения;
- regional node и agent используют отдельные отзываемые секреты, которые хранятся только как хеш и не передаются в URL;
- входной payload имеет лимиты размера, batch, частоты, времени и кардинальности; повтор защищён стабильным ID;
- tracker не собирает form values, текст страницы, cookies, полные IP, fragment и query без allowlist; denylist секретных параметров действует всегда;
- процессы агента не передают environment и командную строку; подробный сбор процессов и кликов включается отдельно;
- raw analytics и metrics имеют ограниченный retention, удаление проекта отзывает ingest credentials до фонового удаления данных;
- CORS и Origin не считаются доказательством подлинности публичной клиентской аналитики.

## Текущее состояние

В проекте реализованы cookie-авторизация, безопасные HTTP/TCP-проверки и heartbeat. Служебные маршруты не раскрывают конфигурацию, строку подключения или внутренние ошибки.

## Секреты

- Реальные API-ключи, пароли и приватные ключи нельзя добавлять в код или документацию.
- Секреты хранятся в локальном `.env` или в менеджере секретов окружения.
- В `.env.example` указываются только имена переменных и безопасные примеры без реальных секретов.
- `.env` уже исключён из Git через `.gitignore`.
- При утечке секрет нужно отозвать и заменить, а не только удалить из последнего коммита.

## Логи

Запрещено логировать:

- пароли и их хеши;
- access- и refresh-токены;
- cookie и заголовки авторизации;
- приватные ключи;
- полные строки подключения с паролями;
- чувствительные пользовательские данные без необходимости.

## Авторизация и права доступа

- Проверки доступа выполняются на backend.
- Каждый запрос к сайту, проверке, инциденту или метрике должен проверять владельца ресурса.
- Нельзя отключать авторизацию для упрощения разработки.
- Пароли хранятся только в виде стойкого хеша с современным алгоритмом.
- Для сессий или токенов должны быть определены срок жизни, отзыв и безопасное хранение.
- Административные действия должны иметь отдельную проверку роли и журнал аудита.

### Реализованные меры

- Пароли хешируются Argon2id с индивидуальной случайной солью.
- Минимальная длина пароля — 12 символов, максимум — 128 байт.
- Случайный токен сессии содержит 32 байта энтропии.
- В PostgreSQL хранится только SHA-256-хеш токена.
- Cookie имеет `HttpOnly`, `SameSite=Lax`, срок 7 дней и `Secure=true` по умолчанию.
- При установке под URL-префиксом cookie ограничивается значением `BASE_PATH` и не отправляется остальным разделам домена.
- Выход отзывает сессию в БД и удаляет cookie.
- Истёкшие, отозванные и принадлежащие удалённым пользователям сессии не принимаются.
- Регистрация ограничена 5, вход — 10 запросами в минуту на IP одного процесса.
- Ошибка входа не сообщает, существует ли указанный email.
- JSON ограничен 16 КиБ; неизвестные поля и несколько JSON-объектов отклоняются.
- Для изменяющих auth-запросов проверяется `Origin`, если браузер его передал.

### Ограничения текущего этапа

- In-memory rate limit не общий для нескольких реплик и сбрасывается при перезапуске.
- Приложение намеренно не доверяет `X-Forwarded-For`; внешний reverse proxy должен иметь собственный rate limit.
- Подтверждение email, восстановление пароля, MFA и завершение всех сессий ещё не реализованы.
- На production обязательно использовать HTTPS и `SESSION_COOKIE_SECURE=true`.
- Первый пользователь создаётся под эксклюзивной блокировкой таблицы и становится владельцем self-hosted-экземпляра. После этого регистрация возвращает `registration_closed`.

## Работа с базой данных

- Использовать параметризованные запросы.
- Не собирать SQL из непроверенных пользовательских строк.
- Изменения схемы выполнять миграциями.
- Пользователь приложения БД должен иметь только необходимые права.
- Резервные копии должны быть зашифрованы и защищены от публичного доступа.
- `DATABASE_URL` обязателен, хранится вне Git и никогда не выводится в лог.
- Миграции применяются в транзакции и используют advisory lock для защиты от одновременного запуска.
- Удаление пользователей и сайтов планируется мягким через `deleted_at`; связанные проверки и инциденты защищены `ON DELETE RESTRICT`.

## Мониторинг пользовательских URL

Проверка произвольных адресов создаёт высокий риск SSRF. До запуска функции необходимо:

- разрешать только ожидаемые протоколы, обычно HTTP и HTTPS;
- запрещать loopback, link-local, multicast, private-сети и адреса метаданных облака;
- повторно проверять адрес после DNS-разрешения и перенаправлений;
- ограничить число перенаправлений;
- установить таймауты, максимальный размер ответа и лимит соединений;
- не передавать внутренние заголовки и учётные данные;
- ограничить частоту проверок для каждого пользователя и сайта.

### Реализовано на этапе управления сайтами

- Разрешены только абсолютные HTTP/HTTPS URL без логина и пароля.
- Блокируются literal IP из loopback, private, link-local, multicast, unspecified и CGNAT-диапазонов.
- Блокируются `localhost`, одноуровневые имена и служебные суффиксы `.local`, `.internal`, `.localhost`, `.invalid`, `.test`.
- Длина URL ограничена 2048 байт, порт — диапазоном 1–65535.
- URL нормализуется до сохранения.

Проверка URL при сохранении сама по себе недостаточна; поэтому реальный HTTP checker выполняет дополнительные сетевые проверки ниже.

### Реализовано в HTTP checker

- DNS выполняется непосредственно перед соединением.
- Если любой полученный адрес относится к loopback, private, link-local, multicast, unspecified или CGNAT, соединение отклоняется.
- Соединение выполняется с уже проверенным IP, что уменьшает риск DNS rebinding.
- Каждый redirect проходит ту же проверку.
- Proxy из переменных окружения не используется.
- Ограничены таймауты и количество перенаправлений; тело ответа не читается.

### Реализовано в TCP checker

- Цель принимается только в форме `host:port`, порт ограничен диапазоном 1–65535.
- Применяются те же запреты на literal IP, локальные имена и служебные суффиксы, что у HTTP URL.
- DNS выполняется перед каждым соединением; соединение разрешается только после проверки всех полученных адресов.
- Dial выполняется по уже проверенному IP с заданным таймаутом, без proxy и без передачи учётных данных.
- В истории сохраняются доступность, время соединения и безопасная ошибка; HTTP status code остаётся `null`.

## Курсоры истории

- Курсор непрозрачен для клиента и содержит только время, ID и усечённый SHA-256-хеш области запроса.
- Область включает владельца, project, monitor, вид истории и точные границы периода; чужой или изменённый курсор возвращает `400 invalid_cursor`.
- До чтения checks/incidents обработчик отдельно подтверждает, что monitor принадлежит проекту текущего владельца; чужие и отсутствующие ресурсы получают одинаковый `404`.
- Base64url и хеш области не считаются механизмом авторизации или шифрованием; доступ всегда повторно проверяется по серверной сессии и владельцу в SQL.

## Heartbeat

- Сырой heartbeat-токен возвращается только при создании monitor.
- В PostgreSQL хранится SHA-256-хеш.
- Неизвестный токен получает тот же `204`, что и правильный, чтобы не раскрывать его существование.
- Токен нельзя добавлять в Git, логи или публичные сообщения.
- Reverse proxy не должен записывать полный путь `/api/v1/heartbeat/{token}` в access log; для heartbeat location нужно отключить или замаскировать access log.
- При подозрении на утечку monitor нужно удалить и создать заново с новым токеном.

## Исходящие webhooks

- Сырой webhook-секрет возвращается только в ответе `201 Created` и больше нигде: списки его не содержат, в логи он не пишется.
- HMAC-подпись `X-UptimeControl-Signature` считается по телу запроса; получатель обязан сверять её через сравнение без утечки времени.
- URL webhook проходит `NormalizeHTTPURL` при создании и перед каждой отправкой.
- Доставка использует общий безопасный транспорт `netpolicy`: без proxy, с DNS/IP-проверкой каждого соединения, максимум 3 редиректа только на публичные URL, таймаут 10 секунд, тело ответа отбрасывается после 1 МиБ.
- Ошибки доставки в `webhook_deliveries`, `notification_attempts` и логах содержат только безопасный код без URL и секрета (сетевые ошибки могут эхом вернуть адрес или Telegram token).
- Один проект ограничен 5 webhooks; очередь выполняет до 8 циклов с ограниченной задержкой и переводит исчерпанные события в `failed`.
- UUID `event_id` входит в подписанное тело и заголовок. Он предназначен для дедупликации at-least-once доставки получателем и не является секретом.
- Переход инцидента и событие очереди записываются одной транзакцией. Аренда через `FOR UPDATE SKIP LOCKED` не даёт двум worker одновременно взять одно активное событие; завершение проверяет ID и номер попытки, поэтому запоздавший worker не перезапишет новый результат.
- Просмотр журнала, пробная отправка и retry проверяют владельца проекта. Retry разрешён только для `failed` и требует `X-Confirm-Retry: true`.
- При подозрении на утечку webhook нужно удалить и создать заново с новым секретом.

## Правило новых зависимостей

Перед добавлением новой библиотеки или внешнего runtime-компонента нужно создать GitHub issue с назначением, альтернативами, лицензией и рисками безопасности. Без такого запроса новая зависимость в проект не добавляется.

## Изоляция сайтов пользователей

- Владелец берётся только из серверной сессии, а не из JSON или URL.
- Просмотр, изменение и удаление используют условия одновременно по `site.id` и `site.user_id`.
- Чужой и несуществующий сайт возвращают одинаковый `404`.
- Удаление мягкое и требует заголовок `X-Confirm-Delete: true`.
- Удалённый сайт выключается, но запись и история сохраняются.

## JavaScript-трекер и аналитика

- Собирать только данные, необходимые для заявленных функций.
- Не собирать содержимое полей паролей, платёжных форм и других чувствительных элементов.
- Ограничить размер и структуру custom events и custom properties.
- Предусмотреть политику хранения и удаления данных.
- Учитывать требования применимого законодательства о приватности и согласии пользователей.
- Защитить endpoint приёма событий от спама и подмены `site_id`.

## Server Agent

- Агент должен использовать защищённое соединение с backend.
- Ключ агента должен иметь минимальные права и возможность отзыва.
- Нельзя передавать аргументы процессов или переменные окружения без явной необходимости: они могут содержать секреты.
- Обновления агента должны иметь проверяемое происхождение и целостность.
- Backend должен валидировать объём и частоту метрик.

## Валидация API

- Ограничивать размер тела запроса и длину строк.
- Валидировать типы, форматы и допустимые значения.
- Использовать rate limit для входа, регистрации, трекера и создания проверок.
- Не возвращать stack trace и внутренние ошибки клиенту.
- Настроить безопасные CORS-политики; не использовать `*` вместе с учётными данными.
- Для cookie-сессий использовать `HttpOnly`, `Secure`, подходящий `SameSite` и CSRF-защиту.

## Перед production-запуском

- провести аудит маршрутов и прав доступа;
- проверить SSRF-защиту;
- включить TLS;
- настроить ротацию секретов;
- настроить резервное копирование и тестовое восстановление;
- добавить мониторинг самого сервиса и оповещения;
- выполнить проверку зависимостей на известные уязвимости;
- реализовать зафиксированные в `DATA_CONTRACTS.md` сроки хранения и процедуру удаления пользовательских данных.
